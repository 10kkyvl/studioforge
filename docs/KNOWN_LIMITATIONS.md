# Known limitations

## Implemented in code, but not reachable from the running product

These packages are written and covered by unit tests, but nothing in the API or app layer calls them, so a user cannot reach them. They are listed here rather than presented as features.

- **`internal/gitops`'s `Detect`, `Init`, and `Checkpoint` methods** have no caller. `Status`, `DiffHead`, `DiffCommit`, `DiffRange`, `SafeRollback`, `SelectiveRollback`, and `Tag` on the same package are wired: `GET /api/v1/projects/{id}/git/status`, the per-run diff panel (below), `GET /api/v1/projects/{id}/diff`, `POST /api/v1/runs/{id}/rollback` (full or, given a `files`/`hunks` body, selective), and `POST /api/v1/projects/{id}/git/tag`. `gitops.Client.Checkpoint` above is a separate, unrelated, still-unused method — the checkpoint actually taken before each non-plan Claude run is `internal/gitcheckpoint.Checkpoint`, which is wired and does work, and its resulting commit is now recorded in the `checkpoints` table and linked to the run, and listable in full via `GET /api/v1/projects/{id}/checkpoints`. A partial rollback takes its own safety checkpoint the same way, but as a `checkpoints` row with no linked run.
- **The path traversal and symlink-escape guard** (`projects.PathGuard.Resolve`) has no caller. No endpoint currently accepts a project-relative path, so registration-time canonicalization is the containment that actually runs. The guard is ready for the first endpoint that needs it.

## Recently wired, with a caveat

- **Task dependencies are enforced when a run starts.** `POST /api/v1/projects/{id}/tasks` accepts a `dependencies` field, validated as a DAG at creation time (a cycle is rejected with 400), and `internal/tasks/readiness.go` walks the full direct-plus-transitive dependency graph before a run may begin. `POST /api/v1/runs` and a user-initiated `POST /api/v1/runs/{id}/restart` both refuse with 409 `task_dependencies_incomplete` (`details.blockers` lists each blocking task's ID, title, and status) unless every dependency has reached `completed`. `POST /api/v1/runs/{id}/resume` and an automatic playtest-correction run skip this check, since both continue a lineage that already started rather than beginning fresh. A dependency that no longer resolves to a task in the same project — deleted, or belonging to a different project — is reported as a blocker with status `missing`; cross-project dependencies stay invalid regardless. The chat task selector and the task board mirror this readiness check client-side to mark blocked tasks and disable starting a run on them, but the server check above is the one that actually gates a run.
- **The per-run diff panel** (`GET /api/v1/runs/{id}/diff`) shows an empty "no changes" state, not an error, for a project that isn't a Git repository of its own — there is nothing wrong, there is just nothing to diff. `?format=structured` returns the same information parsed into `{stats, files}` (per `internal/gitops/diffparse`) instead of a raw diff string, with `note`/`checkpoint`/`studioDirectEdits` behaving identically either way; `GET /api/v1/projects/{id}/diff?from=&to=` answers the same structured model for an arbitrary range between two checkpoints (or `HEAD`), refusing an unrecognized ref with 404 `unknown_checkpoint` and a non-ancestor range with 400 `invalid_range` rather than leaking a raw git error. Rollback can now target a selection instead of the whole checkpoint (`POST /api/v1/runs/{id}/rollback` with a `files`/`hunks` body); it fails closed the same way the full rollback does — a distinct named error for uncommitted changes unrelated to the run, a later run already touching the same path, a reconstructed patch that no longer applies, or a non-git project — and takes its own safety checkpoint before touching anything, so a partial rollback is itself undoable. "Open in editor" from the diff panel, proposed alongside the export affordances, was not built — copy patch (run- and file-level), download `.patch`, and copy path shipped instead.
- **Project memory** (`internal/memory`) now writes one entry per completed run and surfaces up to five relevant past entries into the next run's system prompt. This is intentionally minimal: the entry is the run's own prompt text, not a summary of what the agent actually did or decided, and there is no UI to browse, edit, or delete a project's memory yet.

## Operational limitations

- Same-project multiple writers are intentionally disabled; one writer lease protects each project. Read-only parallel analyzers can be added without changing the resource contract.
- Studio MCP capabilities vary with Roblox Studio. The adapter and mocks are tested, but a real playtest needs an open, MCP-enabled Studio.
- An open Studio is identified only by the single name `list_roblox_studios` reports for it — that listing carries `name`, `id` and `active` status and no place or universe ID, so there is nothing more precise to match on. A place opened from a local file reports that file's name; a place opened from roblox.com, Team Create included, reports its display name instead. A project edited as a roblox.com place is therefore matched by that display name, recorded per project (**Studio sessions → Recognise the project by this name**, or `POST /api/v1/projects/{id}/cloud-place`). Two open places sharing a display name are ambiguous and refused rather than guessed at, and renaming the place on Roblox breaks the match until the new name is recorded. Reading a place's real `PlaceId` would remove both weaknesses but needs a per-instance property read that the listing does not offer.
- StudioForge cannot open a roblox.com place itself: it launches Studio with `-task EditFile -localPlaceFile`, which opens a local build, while a Team Create place is reachable only by being opened from Roblox. Auto-open is therefore suppressed for a project with a cloud place name set — opening the local build would put a second, unrelated window in front of collaborators working in the hosted place — and the run reports what to open instead.
- Studio access is granted to a run only when exactly one Studio instance is open. Claude Code runs its own MCP client, and `set_active_studio` is per-connection state, so StudioForge cannot pin the instance on the agent's connection from outside; the launcher accepts no instance-selection argument either. With several Studios open, access is therefore refused rather than guessed at, and the run continues without Studio. `mcp.Client.SelectStudio` governs StudioForge's own connection only.
- The Studio Sessions view's real-instance discovery (`Provisioner.ListSessions`, `POST /api/v1/studio/sessions/refresh`) is manual, not automatic — nothing polls the launcher in the background, since every probe spawns a launcher process that competes for Studio's single WS host slot. Unlike `Provision`/`Validate`, it deliberately does not refuse on more than one open instance — showing every open one is the point of a listing, not an access grant. Per-instance play state comes from a best-effort `get_studio_state` call after selecting that instance on the daemon's own probe connection; a failure there leaves that one instance's state unknown rather than dropping it from the list or failing the whole refresh. An instance is auto-bound to a project only when its reported name unambiguously matches that project's expected place file name, and only when it was not already bound — a later refresh never overrides an existing manual **Bind project** choice. Under `--mock`, refresh is a no-op; the seeded demo rows are unaffected.
- Studio access applies to Claude and OpenRouter runs, through two different mechanisms (a generated `--mcp-config` naming the shim for Claude, a live per-run MCP client for OpenRouter's in-process loop) that share the same fail-closed provisioner and permission-profile allowlist — neither provider gets a wider grant. The launcher's WS-host contention above affects them differently, though: Claude goes through `studioforge mcp-shim`, so a lost host slot degrades to a cached or fallback tool list rather than losing Studio outright; OpenRouter's loop dials the launcher directly with no shim in front of it, so under the same contention its grant is withheld entirely (a `Studio MCP withheld` notice, no tools at all) rather than degrading gracefully — the run still continues without Studio, exactly like any other withheld grant.
- Studio tools are auto-approved by agent permission profile: `read-only` gets observation only, `workspace-write` adds tools that change the open place, and tools reaching past it (`upload_image`, `store_image`, `http_get`, `user_keyboard_input`, `user_mouse_input`) require `danger-full-access`.
- Rojo live-sync (`POST`/`DELETE /api/v1/projects/{id}/sync`) only carries files into an already-open Studio; it does not eliminate the manual step inside Studio. The Rojo Studio plugin still has to be told to Connect once per session — StudioForge cannot press that button for it — so the chat sync badge's hint exists because the button underneath it is not enough on its own. Edits made to the live DataModel from inside Studio do not flow back to files, and world objects outside the Rojo project tree are unaffected either way; routing those through Studio MCP `multi_edit` instead is faster but desynchronises the DataModel from what git tracks, so it is deliberately a separate path from this one. That desynchronisation is no longer silent: a run that called any Studio tool which changes the open place is recorded as such (`runs.studio_direct_edits`), and the diff panel says so instead of reporting no changes, with the rollback confirmation stating that restoring a commit will not undo them. What is still missing is the tracking itself — the flag says a place-changing tool was used, not what it changed, and there is no way to review or revert those edits from here.
- `--max-turns` does not exist in current Claude Code, so an agent's max-turns limit is dropped by the capability gate and does not bound a Claude run. Budget ceilings still apply.
- The Studio playtest validation loop is opt-in per agent (`validateAfterRun`, off by default) and only runs for Claude and OpenRouter, non-plan runs with `workspace-write` permission or above that actually received a Studio MCP grant; it parses `get_console_output` into records (message, script, line, stack) and classifies on them. **Verified against a live Studio:** `get_console_output` returns bare message text — no timestamps, no severity, no message type — so the only structural signal Roblox leaves is the attribution on a runtime failure (`AssistantCommand:9: attempt to index nil with 'field'`). That attribution is what "structured" means here, and it is trusted regardless of wording. Phrase matching is therefore **not** a fallback for text that failed to parse; it is the fallback for the errors Roblox prints with no attribution at all — `X is not a valid member of Y`, `Infinite yield possible on …` — which carry nothing to key on but their wording. Which route found the failures is recorded per validation (`classifiedBy`); a console with none records nothing, because the Play-mode evidence rather than either route decided the outcome. The residual gap is real: an unattributed failure whose wording matches no known phrase is missed, and `error(msg, 0)` produces exactly that — a bare message with no script, no line and no marker. A pass-like outcome is called `no_errors_detected` rather than `passed`, because nobody plays the game — nothing is clicked, no input is driven, no assertion is made — so what is established is the absence of script errors during startup, not that the change works. It is claimed only when `get_studio_state` confirmed the place entered Play mode; a clean console without that confirmation, and unparseable output with no phrase hits, both resolve to `inconclusive`, since neither distinguishes "nothing went wrong" from "nothing ran". It is fail-open like Studio access itself: an absent launcher, an ambiguous or closed Studio, or a malformed tool response all resolve to `inconclusive`, never to a run failure. A follow-up correction run resumes the same session — the CLI session for Claude, the persisted conversation thread for OpenRouter — and goes through the normal scheduler, so it is bound by the same writer lease and budget ceiling as any other run; a correction that would exceed the project's budget fails with the ordinary budget-ceiling message instead of being retried.
- Operator decisions (`POST /api/v1/decisions/{id}/resolve`) are scoped to exactly one producer: an exhausted playtest-correction budget. The originally-described second trigger — a proposed correction whose permission profile is `read-only` — cannot actually occur, because the validation loop itself never runs for a `read-only` job and a correction always inherits its parent's already-validated permission profile; there is no code path where a read-only correction is ever proposed. Approving submits the exact correction `Job` that was serialized at proposal time, unchanged; denying schedules nothing (the run was already marked `correction_failed` when the decision was first proposed, independent of whether the decision is later approved or denied). This is not a general pre-action approval gate — it never pauses a run before a file edit, a destructive command, or a publish.
- Stuck-run escalation is on by default (`stuck_detection_enabled`, with a per-agent `stuckDetectionDisabled` opt-out) and is separate machinery from operator decisions above — it is built entirely on the same `waiting_decision`/`studioforge-question` mechanism a coding agent's own interactive question already uses, not on the `decisions` table. A run on any provider is paused and handed to the operator as a normal question card when either of two checks trips: no provider event at all — no streamed text, no tool call, no tool result — for `stuck_idle_seconds` (default 600; long local builds and playtests legitimately produce silence, so the default is deliberately generous, which also means a provider hung for nine minutes is not yet flagged), or the same short tool-call cycle has repeated `stuck_repetition_cap` times in a row with no file edit and no newly distinct console/tool-result text in between. Both checks now cover every provider: the repetition heuristic reads Claude Code's `tool_use` blocks and the in-process agent loop's own `tool.call`/`tool.result` events (OpenRouter, NVIDIA) alike, and a file-edit tool from either toolset — Claude's `Edit`/`Write`/`MultiEdit`, agenttools' `create_file`/`replace_exact_text`/`apply_patch` — counts as progress and resets the window. Wall-clock duration and event counts are deliberately not signals — an actively streaming run never trips either check no matter how long it runs, so a run that is "stuck" while still emitting varied output is only caught by the repetition heuristic. That heuristic is intentionally simple — exact repeated-sequence matching over a small rolling window, not semantic understanding of whether the agent is actually stuck — so an agent alternating two genuinely different but textually-similar tool calls can in principle be misread as looping, the same way the validation loop's own phrase-matching can misjudge unusually-worded console output. Clicking **Continue testing** resumes the exact same CLI session with stuck detection suppressed for that resumed run (the operator explicitly said keep going, so it will not re-ask); typing anything else also resumes the session with detection still armed at the current settings; **Stop** cancels the run cleanly instead.
- Pausing a run is a controlled cancel, not a live process suspend: the agent process is actually stopped, the same safe way Cancel stops it. The interrupted turn's partial edits stay on disk exactly as the killed process left them, and `POST /api/v1/runs/{id}/resume` starts a new turn that continues the same saved provider session — not a byte-for-byte revival of the process that was killed.
- If the store write that records a run's terminal state fails, the run is never shown with a fabricated `completed`/`failed`/`cancelled`/`paused` status. The scheduler instead publishes a `scheduler.storage_error` event and leaves the row at its last persisted status, which `RecoverInterrupted` recovers as `interrupted` on the daemon's next restart.
- A Claude run inherits the operator's own Claude Code configuration — `CLAUDE.md`, hooks, plugins and skills — which is billed to every run and makes behaviour depend on the local install. `--strict-mcp-config` isolates the run from the operator's other MCP servers, but only when Studio access was granted; a run without Studio access inherits those servers too. Every Claude run now carries an `--mcp-config` regardless, because StudioForge's own question server lives in one, and that deliberately does not flip the flag on — carrying the question server is not a reason to disable servers the operator configured. Nothing isolates the rest. Claude Code's `--bare` would, yet it requires `ANTHROPIC_API_KEY` and cannot use OAuth or subscription authentication.
- Claude flags are capability-gated. A fake CLI covers stream, malformed, auth, rate-limit, budget, crash, and resume mechanics; actual model availability/cost remains account-specific.
- **The Codex CLI provider has been removed entirely** — no package, no subprocess, no discovery, no `codex_path` setting, no `CODEX_HOME`. Runs saved earlier with `provider="codex"` are not migrated, rewritten, or deleted: they stay fully readable in run history (Codex runs were never checkpointed, so there is no checkpoint to lose; note that OpenRouter and NVIDIA runs are checkpointed as of v0.5.0-rc.2, mock runs still are not, since they change nothing), but they show a **Legacy provider** badge and Restart/Resume return a controlled error instead of trying to relaunch a CLI that no longer runs.
- OpenRouter is an HTTP API, so its adapter has no CLI flags to discover and no `--sandbox`/`--permission-mode` equivalent to delegate to — permission enforcement for its tools happens in StudioForge's own `agenttools` code (see [docs/SECURITY.md](SECURITY.md)). An API key is required to use it at all, including free models, and is stored in the OS secure credential store, never in SQLite. **Free models are less predictable than paid ones**: quality, latency, and rate limits vary more, and a specific free model's availability can change or it can be withdrawn from OpenRouter's catalog without notice — best suited to small tasks, not long unattended runs. StudioForge never silently switches a free-mode run to a paid model to compensate; a model that has become unavailable or lost tool support simply fails the run or is dropped from the picker, and the operator has to choose another one explicitly. Only tool-capable models are offered, since not every OpenRouter model supports tool calling. The model catalog itself is cached for 6 hours with a manual refresh, a last-good-cache fallback, and a bundled dated snapshot as the last resort — none of these guarantee the catalog reflects OpenRouter's current lineup to the minute.
- **`workspace-write` is not a filesystem sandbox — but commands started through `run_command` now run inside real, platform-specific OS confinement.** The `run_command` allowlist refuses the direct escapes (inline `node -e` / `python -c` and their long forms, `go run`, and `npx`), but the allowlisted build tools it does permit — `go test`, `npm run`, `make`, `cargo` — execute project-supplied code by design, and an agent on this profile can write that code first, so the profile means "this agent may run code inside this project," not "this agent is isolated" from what that code can then do. Real OS-level confinement (`internal/processes`) applies only at the one place a model chooses what to run — a process started by the `run_command` agent tool — and nowhere else: not `rojo serve`/`rojo build`/`rojo plugin install` (fixed argv StudioForge itself chooses, and `plugin install` writes into `~/Documents/Roblox/Plugins`), not the Claude Code CLI (it *is* the agent and carries its own permission model; on Windows a job is inherited by every descendant, so confining the CLI would silently apply StudioForge's own caps to every tool call Claude makes), not the Studio MCP shim (local IPC with Studio, needs Studio's own directories), not StudioForge's own `git` checkpoints and operations (need `~/.gitconfig` and credential helpers), not diagnostic probes or the browser launcher, and not the Roblox Studio GUI launch (deliberately detached, so StudioForge exiting does not kill Studio) — plainly, `git` run by an agent through `run_command` is confined, `git` run by StudioForge on its own behalf is not. **On Windows**, a confined command gets its own Job Object, assigned before its first instruction runs (`CREATE_SUSPENDED`, then assigned, then resumed), capped at 128 active processes and 8 GiB job memory, killed with the job and on an unhandled exception, with `CREATE_BREAKAWAY_FROM_JOB` refused; killing goes through the job rather than `taskkill /T`, which walks parent PIDs and loses orphaned grandchildren. **The filesystem is NOT confined on Windows** — a job object bounds processes and memory, not file writes, and there is no filesystem sandbox on Windows without a driver, which StudioForge does not ship. Measured on one machine (`-benchtime 20x`), confinement adds roughly 0.3–0.6 ms per command over unconfined; the fast path is the undocumented `ntdll!NtResumeProcess`, falling back to a ~40 ms documented thread-enumeration path if that call is ever unavailable. **On macOS**, a confined command runs under `sandbox-exec` with a generated profile: writes are denied by default and allowed only under the project root, the temp directory, and the build caches ordinary tooling needs (`~/Library/Caches`, `~/Library/Developer`, `~/.cache`, `~/.npm`, `~/.cargo`, `~/go/pkg/mod`, `~/go/pkg/sumdb`); reads are unrestricted and network egress is deliberately untouched (tracked separately as #29). `sandbox-exec` has been deprecated by Apple since macOS 10.10 and its profile language was never officially documented, so `studioforge doctor` probes it by actually compiling a trivial profile rather than just checking the binary exists; this has so far only been type-checked and cross-compiled locally, not verified against real macOS hardware in this repository — the `macos` CI job (`go test ./internal/processes/...` on `macos-latest`) is what actually exercises it. **On Linux, confinement is not implemented**: `workspace-write` refuses to start a command rather than run it unconfined, and `STUDIOFORGE_ALLOW_UNCONFINED=1` is the named escape hatch for contributors and CI; a specification for what a real implementation would do is written down but not built — see [docs/adr/0005-run-command-confinement.md](adr/0005-run-command-confinement.md). Per profile: `read-only` never registers `run_command` at all; `workspace-write` gets the confinement above and **fails closed** if it cannot be established, refusing the command rather than running it unconfined; `danger-full-access` gets reaping only — nothing outlives a cancelled run — with no filesystem or resource policy, and does not hard-fail, since that profile claims no boundary to fail closed on. `studioforge doctor` reports a `confinement` check describing exactly what is and is not enforced on the running platform; full detail, including the rejected implementation alternatives, lives in [docs/SECURITY.md](SECURITY.md#process-confinement-for-run_command). This is a separate mechanism from the Claude Code path guard described next: on `read-only` and `workspace-write`, StudioForge now also generates a per-run Claude Code settings file (`--settings`, capability-gated) registering a `PreToolUse` hook — `studioforge claude-guard --root <project>` — that resolves the path each file tool was handed against the project root, using the same containment `agenttools` applies to StudioForge's own tools, and refuses anything outside it. The same file denies credential stores (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`) outright, as a backstop for a CLI that honours the settings but not the hook. It is Claude Code enforcing its own settings rather than an OS boundary, it does **not** cover `Bash` — a shell command cannot be reduced to a path, and a heuristic that tried would refuse ordinary work while still missing anything determined — and on `danger-full-access` none of it applies at all, because `bypassPermissions` ignores deny rules and skips hooks. Claude Code's own OS sandbox is unavailable on native Windows.
- `go test -race ./...` requires CGO. This project's default build is `CGO_ENABLED=0` (a CGO-free, single-binary daemon), so `-race` cannot be run locally on a machine without a configured C toolchain — this is unrelated to which provider is in use. CI runs it on `ubuntu-latest`, where a C toolchain is available.
- The portable project archive contains metadata, agents, and tasks. It does not copy source and requires an existing root on import.
- The macOS package is unsigned until a maintainer supplies Apple signing/notarization credentials. The Windows package is likewise an unsigned development build.
- Windows Credential Manager and macOS Keychain are real, active adapters used to store the OpenRouter API key; Claude authentication remains owned by Claude Code, so no Anthropic token is stored anywhere. On a platform or environment where the secure store cannot be reached, the OpenRouter key falls back to an in-memory, session-only value (never written to disk) rather than failing outright.
- There is no asset quarantine, scanning, or Marketplace automation of any kind; automated Marketplace insertion/playtest would in any case require a live Studio MCP session.
- **Run-event retention now prunes automatically.** The `event_retention_days` setting (default 90, `0` disables) bounds how long verbose `run_events` rows survive for terminal (`completed`/`failed`/`cancelled`) runs. A background maintenance loop deletes rows past the cutoff in bounded batches (starting about two minutes after the daemon comes up, then every 12 hours), and `studioforge maintenance --prune-events [--retention-days N]` runs the same prune on demand. Chat-history messages, run summaries, usage/cost, checkpoints, decisions, memory, and projects/tasks/agents are never touched by this — only verbose tool/status/usage events and streaming partial-message chunks age out. There is still no memory-management UI: entries are auto-saved and never pruned or curated.
- **Application logs are redacted, like diagnostic bundles and stored run events.** `internal/security.RedactingHandler` (`internal/security/logredact.go`) wraps the daemon's `slog` handler and reuses the same pattern-based rules — OpenRouter/NVIDIA API key shapes, `Authorization`/bearer headers, cookies, bootstrap/session tokens, API-key query parameters, PEM blocks — replacing a match with `[REDACTED]`. This does not cover the `mcp-shim` subcommand's stdout (MCP protocol traffic) or `studioforge doctor`'s JSON report, since neither goes through `slog`; the diagnostic-bundle writer already has its own separate redaction call site for the latter.
- **The `studioforge_question` tool now covers every coding provider, and the text fence remains only where something other than a model writes it.** OpenRouter and NVIDIA run StudioForge's own in-process toolset. Claude reaches the same tool through StudioForge's own MCP server, `studioforge mcp-shim --questions-only`, which is registered on *every* Claude run rather than only on the ones granted Studio, and which touches no launcher — a machine with no Studio installed still gets it. That server validates the arguments and answers; it has no route back to the daemon and needs none, because the CLI reports its own tool calls with their arguments on the `stream-json` output the scheduler already reads, so observing the call there is the delivery. Which route a question arrived on is recorded on the run event (`channel`). The fence parser stays for the two things that still write one by hand — stuck-run escalation and the mock provider's scripted demo — so a question asked either way renders identically and survives a page reload identically. What is *not* covered: a provider whose CLI does not report tool calls on a stream StudioForge reads would need its own route, and subagents still get no question channel at all, since a subagent's turn ends inside its parent's run and the operator's answer would never reach it.
- **A subagent cannot ask the operator anything.** A subagent's turn ends inside its parent's run and the operator's answer resumes the parent's session, so the subagent that asked is gone before the answer arrives. Subagent prompts therefore carry no question rules at all. Nothing *stops* a subagent emitting the fence by imitation — on Claude, forwarded subagent text reaches the same detector as the lead's own output, and would park the whole run — it is simply no longer described to them as something they can do.
- **Whether a run carries the Roblox interface rules is decided by matching words in the task text** (`prompts.TaskTouchesUI`, English and Russian). It deliberately errs toward yes: a run carrying six lines it did not need costs a little context, while a shop menu built in fixed pixels costs the operator a rebuild after they open the game on a phone. It is still a word list, so an interface task phrased without any of those words gets no rules, and the fuller reference at `.agent/roblox-ui.md` is only read if the agent chooses to open it.
- **`.agent/roblox-ui.md` is written into a project once and never updated.** It is placed when a project is created and on the first run whose task text looks like interface work, and it is deliberately not overwritten afterwards, so an operator's edits survive. The other side of that is that a project created earlier keeps the version it was given: a later StudioForge release's improvements to that document do not reach it unless the operator deletes the file.
- **The prompt changes in this area were measured, on a small sample.** [docs/adr/0003-prompt-ab-results.md](adr/0003-prompt-ab-results.md) records a before/after over real Claude runs: the interface rules take pixel-only sizing from 11 occurrences to 0 across three tasks and introduce aspect-ratio and text-size constraints that no arm without them used at all, and the rewritten correction prompt is the difference between an agent editing a working script because it had no other sanctioned outcome and one reporting the finding as a false positive. It is three tasks per arm and one run per cell, so the large effects are trustworthy and the 13% reply-length result should be read as directional. Two things in #35 remain unmeasured: the `screen_capture`/`get_console_output` instruction, which needs a run holding a real Studio grant, and everything at a sample size worth calling a study.
- **The factual content of `.agent/roblox-ui.md` is verified against a live Studio, not against documentation.** `TestRealStudioUIReferenceClaims` (`internal/roblox/mcp`, behind `STUDIOFORGE_REAL_STUDIO=1`) checks every property default and class the reference names and builds the same interface twice, at a desktop and a phone aspect ratio, to confirm the layout rules behave as written. That is what a wrong rule looks like when it is caught — the reference claimed `ScreenGui.ZIndexBehavior` defaults to `Sibling`, and the probe reported `Global`. Re-run it after a Studio update; nothing else will notice if a default changes.

# Известные ограничения (Русский)

- Несколько writers одного проекта намеренно отключены: один writer lease защищает каждый проект. Параллельные read-only analyzers можно добавить без изменения resource contract.
- Возможности Studio MCP зависят от Roblox Studio. Адаптер и mock протестированы, но реальный playtest требует открытой Studio с включённым MCP.
- Доступ к Studio выдаётся запуску, только если открыт ровно один instance. У Claude Code собственный MCP-клиент, а `set_active_studio` — состояние соединения, поэтому StudioForge не может закрепить instance на соединении агента извне; аргумента выбора instance у launcher тоже нет. При нескольких открытых Studio доступ не выдаётся, а не угадывается, и запуск продолжается без Studio. `mcp.Client.SelectStudio` управляет только собственным соединением StudioForge.
- Обнаружение реальных instance в разделе Сессии Studio (`Provisioner.ListSessions`, `POST /api/v1/studio/sessions/refresh`) запускается вручную, а не автоматически — ничего не опрашивает launcher в фоне, поскольку каждый probe запускает процесс launcher, конкурирующий за единственный WS host slot Studio. В отличие от `Provision`/`Validate`, это не отказывает при нескольких открытых instance — показать все открытые instance и есть смысл списка, а не выдачи доступа. Play state по каждому instance получается best-effort вызовом `get_studio_state` после выбора этого instance на собственном probe-соединении daemon; при ошибке state этого instance остаётся неизвестным, но сам instance не исчезает из списка и весь refresh не проваливается. Instance авто-привязывается к проекту, только если его имя однозначно совпадает с ожидаемым именем файла place этого проекта, и только если он ещё не был привязан — последующий refresh никогда не переопределяет уже сделанный вручную выбор **Привязать проект**. В режиме `--mock` refresh — no-op; демонстрационные строки не затрагиваются.
- Доступ к Studio работает для запусков Claude (через сгенерированный MCP-конфиг, который читает собственный MCP-клиент Claude) и OpenRouter (через собственный живой per-run MCP-клиент StudioForge). Провайдер Codex удалён.
- Инструменты Studio авто-одобряются по permission profile агента: `read-only` только наблюдает, `workspace-write` добавляет изменение открытого place, а инструменты за его пределами (`upload_image`, `store_image`, `http_get`, `user_keyboard_input`, `user_mouse_input`) требуют `danger-full-access`.
- Rojo live-sync (`POST`/`DELETE /api/v1/projects/{id}/sync`) доставляет в уже открытую Studio только файлы; ручной шаг внутри Studio он не убирает. Плагину Rojo всё равно нужно один раз за сессию нажать Connect — StudioForge не может нажать эту кнопку за оператора, поэтому у значка sync в чате есть подсказка: одной кнопки под ней недостаточно. Правки, сделанные в живом DataModel внутри Studio, обратно в файлы не попадают, а объекты мира вне дерева Rojo-проекта live-sync не затрагивает; для них быстрее использовать Studio MCP `multi_edit`, но это рассинхронизирует DataModel с тем, что видит git, поэтому это осознанно отдельный путь. Эта рассинхронизация больше не молчаливая: запуск, вызвавший любой инструмент Studio, меняющий открытый place, отмечается как таковой (`runs.studio_direct_edits`), панель diff говорит об этом вместо сообщения об отсутствии изменений, а подтверждение отката сообщает, что восстановление коммита их не отменит. Чего по-прежнему нет — самого отслеживания: флаг говорит, что инструмент, меняющий place, был использован, но не что именно он изменил, и просмотреть или отменить эти правки отсюда нельзя.
- Флага `--max-turns` в текущем Claude Code нет, поэтому лимит max-turns отбрасывается capability-гейтом и не ограничивает запуск Claude. Бюджетные лимиты продолжают действовать.
- Цикл playtest-валидации в Studio включается по желанию для каждого агента (`validateAfterRun`, по умолчанию выключен) и запускается только для запусков Claude и OpenRouter не в режиме plan, с профилем `workspace-write` или выше, которые действительно получили доступ к Studio MCP. Он разбирает текст `get_console_output` в записи (сообщение, скрипт, строка, стек) и классифицирует по ним. **Проверено на живой Studio:** `get_console_output` возвращает голый текст сообщения — без отметок времени, без уровня, без типа, — поэтому единственный структурный сигнал, который оставляет Roblox, это привязка на ошибке выполнения (`AssistantCommand:9: attempt to index nil with 'field'`). Именно она здесь и означает «структурно», и ей доверяют независимо от формулировки. Сопоставление фраз, таким образом, **не** запасной путь для неразобранного текста: это запасной путь для ошибок, которые Roblox печатает вообще без привязки — `X is not a valid member of Y`, `Infinite yield possible on …`, — где кроме формулировки зацепиться не за что. Путь, которым найдены отказы, записывается по каждой валидации (`classifiedBy`); консоль без отказов не записывает ничего, потому что исход решила не одна из веток, а доказательство входа в Play mode. Остаточный пробел реален: ошибка без привязки, формулировка которой не совпала ни с одним известным маркером, будет пропущена, и `error(msg, 0)` даёт ровно это — голое сообщение без скрипта, строки и маркера. Исход, похожий на успех, называется `no_errors_detected`, а не `passed`: в игру никто не играет — ничего не нажимается, ввод не подаётся, утверждения не проверяются, — поэтому установлено отсутствие ошибок скриптов при старте, а не работоспособность изменения. Он объявляется только когда `get_studio_state` подтвердил вход place в Play mode; чистая консоль без такого подтверждения и неразобранный вывод без совпадений по фразам дают `inconclusive`, потому что ни то ни другое не отличает «ничего не сломалось» от «ничего не запускалось». Цикл fail-open так же, как и сам доступ к Studio: отсутствующий launcher, неоднозначная или закрытая Studio, либо некорректный ответ инструмента дают `inconclusive`, а не провал запуска. Корректирующий запуск продолжает ту же CLI-сессию и идёт через обычный scheduler, поэтому подчиняется тому же writer lease и бюджетному лимиту, что и любой другой запуск; коррекция, превышающая бюджет проекта, завершается обычным сообщением о достижении бюджетного лимита, а не повторяется.
- Решения оператора (`POST /api/v1/decisions/{id}/resolve`) привязаны ровно к одному producer'у: исчерпанному бюджету коррекций playtest. Второй триггер, описанный изначально, — предложенная коррекция с профилем `read-only`, — на практике не может случиться: цикл валидации вообще не запускается для `read-only`-запуска, а коррекция всегда наследует уже провалидированный профиль родителя, так что пути кода, где коррекция с read-only была бы предложена, просто нет. Одобрение отправляет ровно тот `Job` коррекции, что был сериализован в момент предложения, без изменений; отклонение не планирует ничего (запуск уже был помечен `correction_failed` в момент предложения решения, независимо от того, будет ли оно позже одобрено или отклонено). Это не общий gate подтверждения перед действием — он не приостанавливает запуск перед правкой файла, деструктивной командой или публикацией.
- Эскалация "зависшего" запуска включена по умолчанию (`stuck_detection_enabled`, с опцией отключения на уровне агента `stuckDetectionDisabled`) и является отдельной механикой от решений оператора выше — она полностью построена на том же механизме `waiting_decision`/`studioforge-question`, что уже используют собственные интерактивные вопросы агента, а не на таблице `decisions`. Запуск на любом провайдере приостанавливается и передаётся оператору как обычная карточка вопроса, если сработала любая из двух проверок: от провайдера вообще нет событий — ни стриминга текста, ни вызова инструмента, ни результата — в течение `stuck_idle_seconds` (по умолчанию 600; долгие локальные сборки и playtest'ы легитимно молчат, поэтому порог намеренно щедрый — а значит, провайдер, зависший на девять минут, ещё не будет помечен), либо один и тот же короткий цикл вызовов инструментов Studio MCP повторился подряд `stuck_repetition_cap` раз без единой правки файла и без нового отличающегося текста в консоли/результатах инструментов между повторами. Длительность по часам и количество событий сигналами намеренно не являются — активно стримящий запуск не срабатывает ни на одной из проверок, сколько бы он ни шёл, поэтому запуск, "застрявший" с разнообразным выводом, ловится только эвристикой повторов. Эта эвристика намеренно простая — точное совпадение повторяющейся последовательности в скользящем окне, а не смысловое понимание того, действительно ли агент застрял, — поэтому агент, чередующий два по-настоящему разных, но текстуально похожих вызова инструментов, в принципе может быть ошибочно распознан как зацикленный, точно так же, как собственное сопоставление фраз цикла валидации может неверно истолковать необычно сформулированный вывод консоли. Клик по **Continue testing** продолжает ту же самую CLI-сессию с полностью отключённой детекцией для этого продолженного запуска (оператор явно сказал продолжать, повторных вопросов не будет); ввод любого другого текста тоже продолжает сессию, но детекция остаётся включённой с текущими настройками; **Stop** отменяет запуск чисто, вместо продолжения. Начиная с v0.5.0-rc.2 обе проверки работают на всех провайдерах: эвристика повторов читает и блоки `tool_use` Claude Code, и собственные события `tool.call`/`tool.result` внутреннего агентского цикла (OpenRouter, NVIDIA), а инструмент правки файла из любого набора — `Edit`/`Write`/`MultiEdit` у Claude, `create_file`/`replace_exact_text`/`apply_patch` у agenttools — считается прогрессом и сбрасывает окно.
- Пауза запуска — это контролируемая отмена, а не приостановка живого процесса: агентский процесс действительно останавливается, тем же безопасным путём, что и Cancel. Частичные правки прерванного хода остаются на диске в точности в том виде, в котором их оставил убитый процесс, а `POST /api/v1/runs/{id}/resume` запускает новый ход, продолжающий ту же сохранённую сессию провайдера, — а не побайтовое воскрешение убитого процесса.
- Если запись в хранилище финального статуса запуска не удалась, запуск никогда не показывается с выдуманным статусом `completed`/`failed`/`cancelled`/`paused`. Вместо этого scheduler публикует событие `scheduler.storage_error` и оставляет строку с последним сохранённым статусом, который `RecoverInterrupted` восстанавливает как `interrupted` при следующем перезапуске daemon.
- Запуск Claude наследует конфигурацию Claude Code самого оператора — `CLAUDE.md`, hooks, плагины и skills. Это оплачивается в каждом запуске и ставит поведение в зависимость от локальной установки. `--strict-mcp-config` изолирует запуск от остальных MCP-серверов оператора, но только когда доступ к Studio выдан; запуск без доступа к Studio наследует и эти серверы. Каждый запуск Claude теперь всё равно несёт `--mcp-config`, потому что там живёт собственный сервер вопросов StudioForge, и это намеренно не включает флаг: наличие сервера вопросов — не повод отключать серверы, настроенные оператором. Остальное не изолирует ничто. `--bare` изолировал бы, но требует `ANTHROPIC_API_KEY` и не работает с OAuth и подпиской.
- Флаги Claude зависят от discovery возможностей. Fake CLI покрывает stream, malformed output, auth, rate-limit, budget, crash и resume; доступность модели и стоимость зависят от аккаунта.
- Провайдер Codex CLI удалён полностью — не осталось ни пакета, ни поддержки CLI, ни автообнаружения, ни настройки `codex_path`, ни `CODEX_HOME`. Запуски, ранее сохранённые с `provider="codex"`, не мигрируются, не переписываются и не удаляются: они остаются полностью читаемыми в истории запусков (для Codex, как и сегодня для OpenRouter и mock, checkpoint никогда не делался, так что терять нечего), но показываются с меткой **Legacy provider**, а Restart/Resume вместо попытки перезапустить CLI, которого больше нет, возвращают контролируемую ошибку.
- **`workspace-write` — не песочница файловой системы, но команды, запущенные через `run_command`, теперь выполняются в настоящей, платформенно-специфичной OS-изоляции.** Список разрешённых команд `run_command` запрещает прямые обходы (inline `node -e` / `python -c` и их длинные формы, `go run`, `npx`), но разрешённые сборочные инструменты — `go test`, `npm run`, `make`, `cargo` — по своей природе выполняют код из проекта, а агент на этом профиле может сначала этот код записать, так что профиль означает «агент может выполнять код внутри этого проекта», а не «агент изолирован» от того, что этот код потом сделает. Настоящая OS-изоляция (`internal/processes`) применяется только в одном месте — там, где модель сама выбирает, что запустить: к процессу, стартованному инструментом-агентом `run_command`, — и больше нигде: не к `rojo serve`/`rojo build`/`rojo plugin install` (фиксированный argv, который выбирает сам StudioForge, а `plugin install` пишет в `~/Documents/Roblox/Plugins`), не к CLI Claude Code (это и есть сам агент со своей собственной моделью разрешений; на Windows job наследуется каждым потомком процесса, поэтому изоляция самого CLI незаметно применила бы лимиты StudioForge к каждому вызову инструмента Claude), не к Studio MCP shim (локальный IPC со Studio, которому нужны собственные каталоги Studio), не к собственным операциям и checkpoint'ам git StudioForge (нужны `~/.gitconfig` и credential helper'ы), не к диагностическим пробам и запуску браузера, и не к запуску GUI Roblox Studio (намеренно detached, чтобы завершение StudioForge не убивало Studio) — иначе говоря, `git`, запущенный агентом через `run_command`, изолирован, а `git`, запущенный самим StudioForge, — нет. **На Windows** изолированная команда получает собственный Job Object, назначаемый до того, как выполнится первая инструкция дочернего процесса (`CREATE_SUSPENDED`, затем назначение, затем возобновление), с лимитом 128 активных процессов и 8 ГиБ памяти job, завершением вместе с job и при необработанном исключении, с запретом на `CREATE_BREAKAWAY_FROM_JOB`; завершение идёт через job, а не через `taskkill /T`, который обходит по родительским PID и теряет осиротевших потомков. **Файловая система на Windows НЕ изолирована** — job object ограничивает процессы и память, а не запись файлов, и без драйвера песочницы файловой системы на Windows нет, а StudioForge такой драйвер не поставляет. По измерению на одной машине (`-benchtime 20x`) изоляция добавляет примерно 0.3–0.6 мс на команду сверх неизолированного запуска; быстрый путь — недокументированный `ntdll!NtResumeProcess`, с откатом на документированный путь через перечисление потоков (~40 мс), если этот вызов когда-либо окажется недоступен. **На macOS** изолированная команда выполняется под `sandbox-exec` со сгенерированным профилем: запись по умолчанию запрещена и разрешена только внутри корня проекта, временного каталога и кэшей сборки, нужных обычным инструментам (`~/Library/Caches`, `~/Library/Developer`, `~/.cache`, `~/.npm`, `~/.cargo`, `~/go/pkg/mod`, `~/go/pkg/sumdb`); чтение не ограничено, а сетевой доступ намеренно не тронут (отслеживается отдельно как #29). `sandbox-exec` объявлен Apple deprecated начиная с macOS 10.10, а язык его профилей никогда официально не документировался, поэтому `studioforge doctor` проверяет его, реально компилируя тривиальный профиль, а не просто проверяя наличие бинарника; пока это проверено только type-check'ом и кросс-компиляцией локально, а не на реальном железе macOS в этом репозитории — CI-джоб `macos` (`go test ./internal/processes/...` на `macos-latest`) — то, что реально это исполняет. **На Linux изоляция не реализована**: `workspace-write` отказывается запускать команду, вместо того чтобы запустить её неизолированной, а `STUDIOFORGE_ALLOW_UNCONFINED=1` — именованный escape hatch для контрибьюторов и CI; спецификация того, что должна была бы делать реальная реализация, написана, но не построена — см. [docs/adr/0005-run-command-confinement.md](adr/0005-run-command-confinement.md). По профилям: `read-only` вообще не регистрирует `run_command`; `workspace-write` получает описанную выше изоляцию и **отказывает закрыто (fail closed)**, если её невозможно установить, — отказывая в команде, а не запуская её неизолированной; `danger-full-access` получает только reaping — ничто не переживает отменённый запуск — без файловой или ресурсной политики, и не проваливается жёстко, поскольку этот профиль не заявляет границу, на которой можно отказать закрыто. `studioforge doctor` сообщает проверку `confinement`, описывающую именно то, что enforced и что нет на текущей платформе; полные детали, включая отклонённые альтернативы реализации, — в [docs/SECURITY.md](SECURITY.md#process-confinement-for-run_command). Это отдельный механизм от описанного ниже path guard Claude Code: на `read-only` и `workspace-write` StudioForge теперь также генерирует файл настроек Claude Code для конкретного запуска (`--settings`, capability-gated), регистрирующий hook `PreToolUse` — `studioforge claude-guard --root <project>` — который проверяет путь, полученный файловым инструментом, относительно корня проекта, используя ту же проверку, что `agenttools` применяет к собственным инструментам StudioForge, и отклоняет всё за его пределами. Тот же файл прямо запрещает хранилища учётных данных (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`) — как страховку на случай CLI, который соблюдает settings, но не hook. Это Claude Code, соблюдающий собственные настройки, а не граница уровня ОС; `Bash` он **не** покрывает — команду оболочки нельзя свести к пути, а эвристика, которая попыталась бы, отклоняла бы обычную работу и всё равно пропускала бы намеренный обход; а на `danger-full-access` не действует ничего из этого, потому что `bypassPermissions` игнорирует deny-правила и пропускает hooks. Собственная песочница Claude Code на нативной Windows недоступна.

- **Хранение run events теперь очищается автоматически.** Настройка `event_retention_days` (по умолчанию 90, `0` отключает) ограничивает срок жизни подробных строк `run_events` для завершённых (`completed`/`failed`/`cancelled`) запусков. Фоновый maintenance-цикл удаляет устаревшие строки пакетами (запускается примерно через две минуты после старта daemon, затем каждые 12 часов), а команда `studioforge maintenance --prune-events [--retention-days N]` запускает ту же очистку вручную. История чата, сводки запусков, usage/cost, checkpoints, decisions, память и проекты/задачи/агенты этим никогда не удаляются — устаревают только подробные tool/status/usage события и потоковые partial-фрагменты сообщений.
- **Логи приложения теперь редактируются так же, как диагностические архивы и сохранённые run events.** `internal/security.RedactingHandler` (`internal/security/logredact.go`) оборачивает `slog`-handler daemon и переиспользует те же правила — ключи OpenRouter/NVIDIA, заголовки `Authorization`/bearer, cookies, bootstrap/session токены, API-ключи в query-параметрах, PEM-блоки — заменяя совпадение на `[REDACTED]`. Это не касается stdout подкоманды `mcp-shim` (MCP-трафик) и JSON-отчёта `studioforge doctor`, поскольку они не проходят через `slog`.
- **Инструмент `studioforge_question` теперь работает у всех кодовых провайдеров, а текстовый фенс остаётся только там, где его пишет не модель.** OpenRouter и NVIDIA работают через собственный внутренний набор инструментов StudioForge. Claude приходит к тому же инструменту через собственный MCP-сервер StudioForge — `studioforge mcp-shim --questions-only`, — который регистрируется в *каждом* запуске Claude, а не только в получивших Studio, и не трогает launcher: машина без установленной Studio всё равно его получает. Этот сервер валидирует аргументы и отвечает; обратного маршрута к демону у него нет и не требуется, потому что CLI сообщает о собственных вызовах инструментов вместе с аргументами в выводе `stream-json`, который scheduler уже читает, — наблюдение вызова там и есть доставка. Каким путём пришёл вопрос, записывается в событии запуска (`channel`). Парсер фенса сохранён для двух вещей, которые всё ещё строят его вручную: эскалации зависших запусков и сценарного демо mock-провайдера, — поэтому вопрос, заданный любым путём, отрисовывается одинаково и одинаково переживает перезагрузку страницы. Что **не** покрыто: провайдеру, чей CLI не сообщает о вызовах инструментов в потоке, который читает StudioForge, потребуется собственный маршрут; у субагентов канала вопросов по-прежнему нет вообще, поскольку ход субагента завершается внутри запуска родителя и ответ оператора до него не дойдёт.
